# CANopener handheld hardware: the config.txt lines for each part on the Pi's pins.
# The app writes these for you: System > Installed options on the handheld, or
# `canopener-cli hardware --stage 3 --apply` (the Pi installer sets up the helper). It puts them in
# a marked block at the end of /boot/firmware/config.txt. Copy them by hand only on a Pi without the
# app's helper. The helper's table (canopener-boot-config) and core/bootconfig.py match this file.
# Controls are separate: config-controls.txt.
#
# Pins and the reasons for them: docs/ELECTRONICS.md (5.1 Pi header). Then tell the app what's
# fitted, so it never polls a part that isn't there:
#     canopener-cli hardware --stage 2b      (or System > Installed options on the handheld)
#
# Lines marked [verify] are from the docs, not yet run on this hardware: check each with
# `dtoverlay -h <name>` on the Pi before relying on it.
# Keep every line to 98 characters or fewer: the firmware cuts longer ones off without a word (an
# ADS1115 line that ran on lost its last channel's settings that way).

# --- Stage 1: CAN stack A (MCP2518FD on SPI0 CE0, INT on GPIO25, 20 MHz crystal) -> can0 ---
dtparam=spi=on
dtoverlay=mcp251xfd,spi0-0,oscillator=20000000,interrupt=25
# oscillator= must match the crystal (40000000 on the custom board, D10).

# --- Stage 2b: SYNC from the meter Pico GP15 into GPIO21, kernel time stamps -> /dev/pps0 ---
#dtoverlay=pps-gpio,gpiopin=21

# --- Stage 3: ADS1115 on I2C1 (GPIO2/3), address 0x48 -> IIO device "ads1115" [verify] ---
# Only through the divider + clamp front end (ELECTRONICS.md 5.7), never bare probes.
#dtparam=i2c_arm=on
#dtoverlay=ads1115,addr=0x48,cha_enable,chb_enable,chc_enable,chd_enable

# --- Buttons and battery: a second ADS1115, ADDR to 3.3 V -> address 0x49 (option button_adc) ---
# A0 the battery pack through a 100k / 15k divider; A1-A3 the button stacks (docs/DEVICE.md). The
# ads1115 overlay is loaded twice, once per address (works: seen on the prototype), and shows as two
# IIO devices named ads1015, one under 1-0048 and one under 1-0049. 73-canopener-adc.rules (install.sh
# --device) sets every input to 860 samples a second.
#dtparam=i2c_arm=on
#dtoverlay=ads1115,addr=0x49,cha_enable,chb_enable,chc_enable,chd_enable

# --- Stage 5: CAN stack B (MCP2518FD on SPI0 CE1, INT on GPIO20) -> can1 ---
#dtoverlay=mcp251xfd,spi0-1,oscillator=20000000,interrupt=20

# --- Instead of stacks A and B: Waveshare 2-CH CAN FD HAT, as shipped (option can_hat) [verify] ---
# Two isolated MCP2518FD channels, 40 MHz, own 8-26 V input. CAN_0: SPI0 CE0, INT GPIO25.
# CAN_1: SPI1 (MISO 19, MOSI 20, SCLK 21, CE0 GPIO18), INT GPIO24. That second channel takes the
# SYNC input's pin (GPIO21) and the buzzer's (GPIO18), so the app leaves sync out while the HAT is
# on, and the encoder's A line moves from GPIO24 to GPIO7 (SPI0's CE1, which the HAT doesn't use:
# spi0-1cs frees it; config-controls.txt has the line to change). With the button ADC too, the
# buttons leave the GPIOs altogether and the encoder is on 17 / 27.
#dtparam=spi=on
#dtoverlay=spi0-1cs
#dtoverlay=mcp251xfd,spi0-0,oscillator=40000000,interrupt=25
#dtoverlay=spi1-1cs
#dtoverlay=mcp251xfd,spi1-0,oscillator=40000000,interrupt=24

# --- Stage 6: ESP32 on the GPIO14/15 UART -> /dev/ttyAMA0 ---
# Turn the serial console off first (raspi-config > Interface Options > Serial Port:
# login shell No, serial hardware Yes).
# Pi 5:
#dtparam=uart0=on
# Pi 3B+ (frees the PL011 UART from the onboard Bluetooth):
#enable_uart=1
#dtoverlay=disable-bt

# --- Optional: PWM buzzer on GPIO18 (I2S audio is given up for GPIO19-21) ---
# As in deploy/raspberry-pi/README.md; [verify] the func= value on the Pi 5's RP1. With the
# Waveshare HAT, GPIO18 is its own: with the button ADC, GPIO12 or 13 (also PWM) are free for it.
#dtoverlay=pwm,pin=18,func=2

# take any SPI TFT hat off first: it sits on SPI0 with the CAN controller.
